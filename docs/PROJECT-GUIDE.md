# 企业数据变更治理与智能执行平台全景介绍

## 一、系统概述

企业数据变更治理与智能执行平台面向数据仓库、数据湖、实时任务、消息主题、指标和 BI 等数据资产，解决数据变更过程中“影响看不清、风险难判断、审批缺依据、发布不可控、异常难恢复、过程难审计”的问题。

平台以 `Data Change` 为统一治理对象，将一次数据变更从需求建档、影响分析、契约验证、质量检查、人工审批，一直管理到 Shadow、Canary、生产观察、回填和恢复。每一个关键判断都关联证据，每一次执行都生成回执，每一次状态变化都可追溯。

当前版本已经形成可独立运行的治理控制面和完整演示闭环。默认采用本地安全模式，不连接生产系统、不产生生产副作用；真实数据库、Kafka、Flink、元数据平台和工作流平台可在后续工程化阶段接入。

## 二、建设目标与业务价值

| 建设目标 | 解决的问题 | 形成的能力 |
| --- | --- | --- |
| 变更可知 | 不知道改动影响谁、风险多大 | 资产发现、字段血缘、影响分析、风险评分 |
| 变更可控 | 仅靠人工经验审批和上线 | Contract、质量门禁、分级审批、Shadow、Canary |
| 变更可恢复 | 发布失败后依赖临时人工处理 | Recovery Plan、补偿流程、回填与恢复执行回执 |
| 变更可审计 | 缺少审批依据和操作证明 | Evidence、状态历史、Release Bundle、Execution Receipt |

业务上，平台将分散在需求单、聊天记录、SQL 脚本、调度平台和人工审批中的治理活动，归并为一条有明确对象、规则、责任人和证据的标准流程。

## 三、功能全景

### 1. 数据变更治理中心

系统支持 Schema、语义口径、数据管道、指标、数据源和质量规则等类型的变更。创建变更时记录业务目的、目标资产、变更前后定义、负责人、消费者数量、目标环境、破坏性标识和恢复计划。

变更由状态机统一管理，覆盖 20 个业务状态，包括草稿、资产发现、影响分析、验证、等待审批、审批驳回、Shadow、Canary、生产观察、完成、回滚和恢复等。非法跨阶段操作会被服务层直接拒绝。

### 2. 影响分析与风险评估

平台基于资产等级、下游消费者、破坏性、影响范围和恢复条件计算风险分值，并归类为 LOW、MEDIUM、HIGH 或 CRITICAL。

影响结果严格区分：

- `CONFIRMED`：由正式血缘或人工核验确认，可参与风险计算和发布门禁。
- `CANDIDATE`：由推断或智能分析发现，只用于提示，不能直接阻断或放行。
- `REJECTED`：经人工核验不成立，保留驳回人与理由。

候选血缘支持人工确认和驳回；只有确认后才进入确定性影响集合。

### 3. Data Contract 生命周期管理

Data Contract 管理资产的 Schema、业务语义、质量策略和向后兼容要求。系统支持草拟、版本校验、发布、退役和版本历史查询。

新版本发布时，平台对当前生效版本执行兼容性检查，可识别字段删除、精度收窄、Nullable 收紧、主键移除、枚举收缩和时间精度丢失等风险。发布成功后，旧版本自动退役，确保同一资产只有一个生效版本。

### 4. 质量规则与处置闭环

质量规则按资产配置，包含指标、阈值、严重度和负责人。执行后保存实际观测值、阈值、PASS/WARN/BLOCK 结果及执行时间。

异常结果支持确认、豁免和解决。任何处置都必须填写人员和原因；未处置的 BLOCK 结果会阻断质量门禁，完成有效处置后平台自动重新计算门禁状态。

### 5. 分级审批与业务待办

平台根据风险等级生成审批任务：基础审批由 Data Owner 负责，高风险和严重风险额外要求 Governance Admin 审查。

审批按任务逐项处理，支持通过、驳回、修改后重新提交。部分任务通过不会放行；只有全部审批任务完成后，平台才生成不可变 Release Bundle 并允许进入发布验证阶段。

提交审批、风险审查、驳回和全部批准会生成站内通知。通知支持按接收人查询、未读统计和标记已读。

### 6. 受控发布与恢复

审批通过后，平台将资产、变更内容、契约状态、质量状态和恢复条件冻结为 Release Bundle，并计算 SHA-256 摘要，防止审批后执行内容被静默修改。

发布过程覆盖：

```text
Release Bundle → Shadow 完整窗口对账 → Canary 5%/25% → Promote → 生产观察
                                               ↘ Backfill / Recovery
```

每个执行动作使用稳定幂等键，默认 Attempt Budget 为 3，并生成 Execution Receipt，记录动作、连接器、资源版本、Trace ID、执行次数、结果和耗时。

### 7. 证据与审计

系统将治理依据分为人工输入、正式血缘、规则验证、执行回执、发布清单和智能结论等类型。Evidence、状态历史、审批任务、质量结果、Release Bundle 和 Execution Receipt 共同形成完整证据链。

治理人员可以回答四个关键问题：为什么允许变更、谁批准了变更、实际执行了什么、失败时如何恢复。

### 8. 智能治理

平台提供四类治理 Skill：

| Skill | 主要作用 |
| --- | --- |
| Requirement | 提取资产范围、业务口径、验收条件和责任边界 |
| Impact | 发现正式血缘之外的长尾候选依赖 |
| Quality | 建议对账维度、阈值和观察窗口 |
| Incident | 结合 Trace、回执和故障模式生成恢复建议 |

智能能力默认使用本地确定性 Provider，不要求 OpenAI API。无论后续使用本地模型、企业模型还是外部模型，输出都只能先成为 `CANDIDATE` Finding，并且必须携带知识引用；人工验证后才能转化为正式 Evidence。

系统内置 Golden Case 与 Bad Case Replay，用于检查模型或规则升级后是否发生能力退化或越权行为。

### 9. 治理门户与运营报表

当前门户提供治理总览、变更工作台、资产与血缘、策略与门禁、证据与审计、智能治理、连接器和可观测性视图。

治理运营报表集中统计变更总量、待审批数量、阻断数量、生效/草拟 Contract、未关闭质量问题、确认/候选血缘，以及按风险和状态的分布，为治理团队提供业务积压和风险态势视图。

## 四、阶段成果

### Phase 1：基础治理闭环

完成 Data Change、影响分析、风险评估、Contract/质量门禁、审批、状态历史和治理工作台，打通从建档到验证的基础流程。

### Phase 2：受控执行与恢复

完成不可变 Release Bundle、幂等执行、Attempt Budget、Execution Receipt、Shadow、Canary、Promote、Backfill 和 Recovery，形成可回放的发布与恢复链路。

### Phase 3：智能治理

完成四类治理 Skill、版本化知识库、Candidate Finding、人工 Evidence Verification、Golden/Bad Case Replay，并支持无需外部 API 的本地智能 Provider。

### 业务收口增强

进一步完成逐任务审批、驳回重提、Contract 版本生命周期、质量异常处置、站内通知、候选血缘人工核验和治理运营报表。

## 五、产品与技术亮点

1. **事实与候选分离**：正式血缘、人工确认事实与模型候选严格分层，避免智能推断污染治理事实。
2. **审批内容冻结**：审批完成后生成带 SHA-256 的 Release Bundle，保证“审批的内容”和“执行的内容”一致。
3. **规则优先、智能辅助**：确定性门禁负责放行，智能能力负责补充发现和建议，Agent 无权直接推进生产状态。
4. **全过程可回放**：状态历史、证据、审批、质量处置和执行回执可以还原一次变更的完整过程。
5. **发布与恢复对称设计**：不仅描述如何上线，也将 Backfill、Recovery 和补偿动作纳入同一状态机。
6. **本地优先、模型可替换**：不绑定 OpenAI API；通过统一 Provider 接口可替换为 Ollama、企业内网模型或其他服务。
7. **默认无生产副作用**：演示环境使用 `LOCAL_SAFE` 执行边界，可完整验证业务流程而不误操作生产资源。
8. **模块化单体落地**：在业务尚未稳定前保持部署简单，同时为元数据、工作流、消息和执行连接器保留清晰替换边界。

## 八、总体评价

当前项目已经从设计文档发展为一个可运行、可演示、可回归验证的治理产品原型。其核心成绩不只是实现页面或接口，而是建立了三条稳定边界：确定性事实与智能候选分离、审批决策与执行内容一致、发布动作与恢复证据可回放。

这使平台具备继续接入真实企业数据环境的基础，同时避免在业务规则尚未稳定时过早绑定某一家模型厂商或重型基础设施。
